# TRAE CN MCP 实施与验证

日期：2026-09-02。环境：Windows、Node 24.13.0、TRAE CN 2.3.77497（内部 VS Code/TraeCN 1.107.1）、Chromium 142、CDP 1.3。插件版本 `0.1.0-alpha.5`，未安装。

## 发行来源与边界

生产实现不依赖 `third-part-research/`。构建输入是 npm 官方 registry 的 `@luckycat133/traecnclaw@0.6.0` tarball，MIT，SHA-1 `d61700fe037a504b17060ec99337021e72698a1f`，SHA-512 SRI `sha512-4wCZmtskz5Cge/rF474OxsfAvTux1ln0Ry63V9JW3vLS8mcZMjivO69UZ4gHJ9rHy5rEJ9UeGzMrhdO4RC5DcA==`。归档共 171 个文件；与本机历史副本对比，165 个相同，6 个差异都对应已知 Windows/package 补丁。构建脚本每次先验证 SRI，再以精确上下文断言应用补丁；上下游版本漂移会使构建失败。

随插件保留 tarball、`UPSTREAM.json`、第三方通知和 TRAECNclaw、ws、MCP SDK、zod、esbuild 的许可证文本。发行 bundle 不读取登录态文件，不直调 TRAE 私有模型 API。

## 工具与安全收敛

Codex 只看到四个工具：`trae_probe`、`trae_submit`、`trae_status`、`trae_result`。stdio 服务调用随插件发布的本地 HTTP 网关；网关由用户显式前台启动，服务和插件安装都不会启动或结束 TRAE。

相对上游增加以下约束：

- Windows durable-copy 以 `r+` 打开复制后的文件，使 `FlushFileBuffers` 可用；目录 fsync 的捕获型 EPERM 仍可能只作为噪声日志出现。
- Lexical composer 使用 DOM Selection API 选中内容，再 Backspace 与 `Input.insertText`，避免 Ctrl+A 焦点竞态。
- `TRAECN_STRICT_CDP_PORT=1` 只允许指定的 9223。测试发现上游默认扫描会在 TRAE 未启动时误选 9222 上的 DoubaoWork，甚至可能把通用选择器命中当作 ready；正式 bundle 已关闭扫描。
- `/api/tasks/submit` 的自动继续和对话自动审批被强制关闭。模型错误、结果检查和完成检查的后台重试默认均为 0，启动器再次显式设置 0。
- MCP 在发送前以 TRAE 进程、workspace surface、workbench URL/标题共同确认应用身份；请求 UUID 先原子登记，发送状态未知时不自动重放。提示词不写入 MCP 状态文件，只保存摘要；上游网关的外部 task-history 仍会持久化任务文本和结果。
- 不公开上游 cancel：上游可能在停止生成失败时仍把任务写成 cancelled。本地观察到 cancelled 时返回 unknown。

## 自动化验证

TRAE 子项目共 8 项测试通过：四工具白名单、严格 CDP 隔离和持久状态、TRAE/其他 Electron 身份区分、发送前拒绝、UUID 幂等与冲突、审批态映射、稳定结果、取消和不稳定结果处理。构建脚本的精确计数断言同时验证安全补丁确实应用到该版本上游。

stdio 冒烟测试完成 initialize 与 tools/list。网关冒烟测试用动态空闲端口启动真实 bundle，确认版本 0.6.0、未误连其他 CDP、durability 未降级；测试结束后端口关闭，无残留网关进程。

## 真实运行

使用专用 `127.0.0.1:9223` 启动 TRAE，`/json/version` 返回 Chromium 142 / CDP 1.3。启动时不能传 `--remote-debugging-address`：当前 TRAE 把它当作未知主进程选项；GUI 进程也不能继承会在命令结束时关闭的 stdout/stderr，否则日志写入触发 EPIPE。用 `ProcessStartInfo` + `UseShellExecute=true` 启动后，workbench 标题为 `uAgents - TraeCode CN`，网关 readiness 命中 Solo composer、发送按钮和响应区。

真实 MCP 请求 `dabb7f30-f216-4ce6-a4cd-d9519c4348f1` 完成了 probe、submit、status、result 全链，获得原生任务 ID `task_1_mtiz4bi0_32z6zoowp4`，经历 queued/executing 后由 TRAE 原生返回 failed。Solo 面板明确显示“积分不足，你还有 TraeWork 专属积分，可前往使用”，网关错误为 `Trae model request failed`；MCP 正确返回 failed，没有把 UI 文本或旧回答认作成功。

该真实调用暴露了上游默认会在模型错误后重试 3 次。随后已应用上述零重试与零自动审批补丁并重建、回归通过。由于当前 TRAE CN 额度已不足，没有再次发送模型请求来消耗其他路线或验证补丁后的服务端成功回答。本机 2026-08-30 历史记录证明同一 TRAECNclaw/CDP/Solo 路线曾返回真实“测试成功”，但这份历史证据不能替代当前版本的成功终态。

## 剩余限制

Windows 仍由 `traecn-unknown` degraded 适配器处理，成功结果可能包含整块 Solo 面板文本。首开新工作区的信任弹窗必须由用户处理。当前没有跨 MCP 进程的额外窗口锁；共享网关的上游持久队列负责串行，但多个独立网关实例仍应避免同时控制一个窗口。插件未安装、未注册个人 marketplace，未修改全局 `AGENTS.md`、登录配置或供应商设置。
