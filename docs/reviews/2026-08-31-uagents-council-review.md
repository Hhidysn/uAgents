# uAgents 插件方案会审

日期：2026-08-31。范围：方案评审与资料归档核对；没有实现、安装或运行插件。

## 结论

保留一个 Plugin、一个按需加载的 `agent-dispatch` Skill，以及 TRAE、豆包工作两个独立 MCP 服务。agy、WorkBuddy、OpenCode 继续通过 CLI 接入，没有必要现在增加统一 MCP 或为每个 CLI 拆一个插件。

设计已经说明了需要哪些保障，但部分保障还缺少可验证的机制。建议补齐首个 CLI 切片的生命周期、权限和重复提交契约后再实现；桌面窗口与豆包完成判定的细节，在进入对应阶段前补齐。本报告是待审阅的修订建议，不代表用户已批准全部机制或插件实施。

## 需要补齐的五项机制

P1 表示进入相关实现阶段前应解决的关键契约，P2 表示需收窄或补充的设计；不是已经复现的代码缺陷。

| 优先级 | 设计位置 | 发现与影响 | 建议与验收证据 |
| --- | --- | --- | --- |
| P1 | 第 4.3、5、10 节 | worker 如何生存、谁维护状态、后续从哪里查询或取消未确定；短工具调用结束可能使任务失联 | 先用可控模拟 worker 验证提交端退出后仍完成并产生可查询产物；记录进程创建时间和运行标识，不能只认 PID。明确支持哪种退出边界，再决定是否需要监督进程 |
| P1 | 第 5、7 节 | `analysis` 和 `owned_paths` 是输入声明，各适配器实际能强制什么限制尚未映射 | 列能力矩阵：只读、允许目录、工具/网络边界、会话续接、取消和完成证据。不支持请求所需限制时拒绝，或向主模型返回可缩小的范围；不能偷偷改成仅靠提示词约束 |
| P1 | 第 5、7 节 | request_id 去重的落盘时点、请求冲突和发送后断线未形成协议，可能重复执行或重复消耗额度 | 发送前原子登记提交意图；相同请求返回已有记录，内容不同则冲突。已发送但确认丢失时进入待核对状态，不能自动重发 |
| P1（桌面阶段） | 第 7 节 | 跨进程窗口锁只写了要求，未定义所有者与失效恢复，多个 Codex 调用者可能操作同一会话 | 确定应用/窗口身份、任务所有者和锁载体；锁超时或本地进程退出后，仍须核对上游任务是否在运行。无法核对时保持占用/未知，不能仅因租约过期就接新任务 |
| P2 | 第 3、4.3、9、10 节 | `.mcp.json` 的“两个服务就绪后才声明”与先交付 TRAE 不一致；脚本定位 runtime、缺应用时初始化行为未钉牢 | skills-only 包保留合法插件 manifest；TRAE 就绪时仅声明 TRAE。入口按发行文件位置定位 runtime，不依赖当前工作目录、研究目录或本机缓存路径。应用未启动时仍能初始化 MCP，任务工具报告不可用 |

重复提交建议使用经过校验的 `request_id` 与规范化 target 组成键，并比较完整有效请求摘要，至少包含模型、工作目录、权限范围、提示词及上下文内容摘要。不能只比较 prompt，也不能把未校验的请求标识直接拼成文件路径。确切摘要字段和默认值应在首个适配器实现前固定。

取消请求不等于任务已取消。本地 CLI 已退出，也不证明远端生成或桌面任务停止；确认不了时保留原始任务标识和未知状态。并发取消、进程身份不符及重启后的恢复都应有明确返回结果。

## 不直接采纳的评审建议

- **把 detached 当成 Windows 生存保证。** Node 文档介绍了 detached、unref 和脱离父进程 stdio 的条件；Windows job 的子进程关联与 breakaway 又受 job 配置约束。因此不能从 detached 一个参数推断已经解决宿主回收问题，必须在实际运行环境验证。依据：[Node 子进程文档](https://nodejs.org/api/child_process.html#optionsdetached)、[Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。
- **把事后文件 diff 当成只读隔离。** 差异检查能发现部分越界，不能阻止写入，也不能证明未发生其他副作用；只能作为补充证据。
- **将连接已有 CDP 等同于开启 CDP。** 这是不同操作。采纳的是按需连接和故障隔离要求，不采纳这种等同；本轮没有复现 MCP 初始化故障。
- **把回复静默一段时间当成豆包任务成功。** 静默只能辅助观察，还需任务/消息归属和可信完成信号。无法可靠识别时报告未知，不能把旧回复或暂停中的生成当作结果。
- **窗口锁到期便直接释放。** 本地控制者可能失联而远端任务仍运行；释放前需要上游状态核对，锁实现本身也不能约束用户手动切换会话。
- **首个可安装包省略 manifest，或把退出后 unknown 算作存活测试通过。** 前者只算脚本原型；后者只能证明错误报告诚实，不能证明后台任务继续完成。

上述判断来自契约审查和相关官方资料，不是本轮插件运行测试的结果。

## 两份外部意见的侧重点

候选 A（DeepSeek Flash）着重指出后台 worker、窗口锁、只读执行、去重与队列归属，还追问 MCP 连接时机。关于队列，建议首版 CLI 不自建持久队列；若桌面窗口忙，则返回明确的 busy。若复用 TRAECNclaw 已有队列，应保留其真实契约与状态，不伪造排队或盲目移除上游能力。

候选 B（GLM-5.2）除共同问题外，着重指出 Skill 脚本与插件级 runtime 的定位契约、同一 request_id 内容冲突，以及豆包完成识别。其“宿主只复制 Skill 会导致 runtime 缺失”是待验证的假设，不能写成已确认的 Codex 行为。

主模型另提出状态保存与清理边界：必须区分用户需要取回的任务结果和可选诊断日志；后续确定结果保留期、容量上限与活跃任务保护，不能因为默认不记完整日志就丢失唯一答案，也不能在插件更新时自动清除任务记录。

## 建议的第一步

把原阶段 1 的三个 CLI 拆成较小的验收单元，避免一次验证全部路线。

1. **运行机制验证：** 不调用付费模型，用模拟 worker 检查提交、结果查询、提交端退出、超时、取消、重复请求、冲突、中文/空格路径及恢复。成功场景必须实际完成；故障场景必须准确报告，不以 unknown 代替成功。尊重宿主的安全限制，不通过关闭安全策略实现后台存活。
2. **单一 agy 切片：** 按用户优先级先接 agy，验证可用 CLI/模型、实际权限控制、原生会话 ID、结果和产物归属。若权限能力不满足任务边界，明确阻断该模式，不能为演示闭环而放宽权限。前端/美术建议与实际生成图片的能力分别验收。
3. **再扩展：** 复用已验证契约接入 WorkBuddy 和 OpenCode council；随后进入 TRAE，最后豆包。每个阶段仅在插件清单声明确实存在且通过验收的组件。

此顺序不承诺新增守护服务、数据库或队列。优先验证原生会话、现有宿主能力和标准库；只有确有证据表明不够时，再选择最小额外组件。
