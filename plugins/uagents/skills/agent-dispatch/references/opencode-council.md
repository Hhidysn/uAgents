# OpenCode execution

Use `target=opencode` and an explicit `provider/model` ID. Native-discovered `configured=false` entries can be selected directly and use the target's native file/image mapping; per-model acceptance remains unconfirmed until native evidence exists. Both `analysis` and `implementation` are supported, and declared workspace-relative file or image inputs are passed to OpenCode as native repeated `--file` arguments after snapshot verification. Check route-level `input_support` for the evidence level. The built-in routes are:

- `commandcode-goat/deepseek/deepseek-v4-flash`
- `commandcode-goat/z-ai/glm-5.3-flash`

The adapter verifies the installed CLI version before building run arguments. OpenCode V1 uses `opencode run --model <route> --format json --dir <workspace> --title <task>`; V2 omits `--dir` because the transport already starts the process in the task workspace. Both send the prompt over stdin. V2 model discovery runs `opencode models` once and filters the configured provider IDs; V1 keeps provider-specific discovery. For an intentional follow-up, create a new Task with `session.continue_from_task_id=<previous-task-id>`; uAgents resolves the previous Task's persisted native session and runs `opencode run --session <session-id>` for the new prompt in the same workspace. To create an independent branch from the same context, use `session.fork_from_task_id=<previous-task-id>`; uAgents runs `opencode run --session <session-id> --fork` and requires the native event stream to bind a new session ID. It does not add `--pure` or `--auto`; pass those and other non-conflicting OpenCode options in `execution.native_args` in the requested order. Dispatcher-owned `run`, `--model`, `--format`, `--dir`, and `--title` arguments cannot be overridden, and structured continuation/fork cannot be combined with caller-supplied `--session`, `--continue`, or `--fork` selection. V1 `--pure` disables OpenCode plugins; it is not an enforced read-only sandbox. V2 removed `--pure` and uses `provider/model#variant` for variants. Check `opencode run --help` before supplying version-specific native arguments. Declared `expected_outputs` remain optional and use the shared artifact capture/verification pipeline when present.

On Windows, the current source runs OpenCode tasks through the durable execution controller, including explicit continuation and fork turns. uAgents persists a provisional workspace/process guard before spawn, verifies PID + start time + executable before the first prompt byte, writes stdout/stderr to task-local transcript files, and stores the native session as soon as the first valid OpenCode event exposes it. If the observing Worker disappears, `resume`/`reconcile` can recover the same Attempt by reading that persisted process/transcript evidence and the persisted session action. Recovery never automatically starts another `opencode run --session`, `--continue`, or `--fork` and never resends the original prompt; it may remain `indeterminate` when terminal evidence is insufficient. A new native turn or branch is represented by a new Task using the structured `session` selector, not by `resume`.

V2.0.21 can emit `step_start` and `text`, then exit zero without `step_finish`. The adapter now queries `session export` for that exact session after native exit, and also during same-Attempt reconciliation. Success requires matching workspace, final assistant message ID, completed/idle times, provider/model and final text. The raw export remains in memory only. Failed/missing evidence stays `indeterminate / native_completion_unconfirmed` with partial text preserved; text plus zero exit alone is insufficient. Real text completion and same-Attempt recovery passed for the selected Go DeepSeek and GLM routes; continuation/fork and attachments still need their own real V2 E2E.

An alive or uncertain durable OpenCode process keeps overlapping workspaces guarded even after the Worker lease expires. `observation_timeout_ms` and a cancel request stop the current observer but are not proof of native/provider cancellation; uAgents does not kill the durable process merely because observation ended. Platforms without equivalent PID/start-time/executable ownership inspection currently keep the previous uninterrupted OpenCode transport.

Windows OpenCode also supports `execution_timeout_ms` in the current source. The current reliability follow-up uses two detached per-Attempt timeout guardians and requires distinct PID-bound durable ready handshakes before uAgents records `possibly_sent` or writes the first prompt byte. The deadline begins at that durable send checkpoint and survives Worker death; one guardian can also fail after ready while the other continues. At expiry the guardians serialize through a short-lived fenced claim, and only the current claimant may persist timeout/process/guard state. uAgents terminates only a PID/start-time/executable-matched process tree, then re-inspects the root and descendants; the workspace guard is released only after quiescence is proved. `execution_timeout` means that local deadline enforcement found the owned tree quiescent at/after the deadline, not that the OpenCode provider/session acknowledged cancellation, so the unified task result remains conservative (`indeterminate`) unless stronger native terminal evidence exists. `execution_timeout_termination_unconfirmed` keeps the workspace guarded.

V2 tasks with `execution_timeout_ms` use a private `--standalone` server so the owned process tree includes execution. A conflicting `--server` is rejected before send. This does not retroactively stop old shared-server sessions or prove Provider-side cancellation.

The JSON event stream identifies the native session and final message parts but does not independently report the model. Calls verified through the V2 session export record the matching runtime model as `model_reported` with `model_verified=true`; other calls keep the unverified evidence state.

Provider error events are reduced to a redacted structured failure. Authentication rejection is reported as `authentication_required` with the HTTP status and native error class only; response headers, response bodies, and credential material are discarded. The version-only probe does not authenticate with the provider, so a successful probe does not establish that a live model call will succeed.

V2 may recover an intermediate Provider error in a newer assistant message while still exiting with code 1. uAgents confirms that recovery only when a bounded export proves the same session/workspace, that exact newer final message, matching model/text, and successful completed/idle state. Missing or mismatched proof preserves the failure; a final-message error or approval wait cannot be overridden. Already-persisted terminal Task states remain immutable, so a hotfix does not automatically correct a historical failed Task.

On the preferred local path, the OpenCode process inherits the invoking terminal environment through the detached uAgents worker. Provider-specific subscription variables are not named in plugin code. A plugin MCP server may receive a restricted environment even when direct OpenCode works; use the local uAgents CLI when available instead of treating that MCP-only authentication failure as a Provider outage.

For multi-Agent work, prefer the first-class Council API instead of manually creating unrelated Tasks. The default is `analysis + shared`; parallel implementation candidates use `mode:"implementation"` with `workspace_strategy:"git-worktree"`. Compare with `council-diff`, optionally run explicit local test argv with `council-validate`, explicitly apply one succeeded candidate with `council-adopt`, then explicitly remove no-longer-needed candidate worktrees with `council-cleanup`. Council performs no automatic vote, synthesis, commit, merge, cleanup, winner selection, or provider replacement. Full lifecycle semantics are in [council.md](council.md). Native OpenCode session fork remains same-target; cross-target Council members share context through the common prompt/attachments, not through a native session.
