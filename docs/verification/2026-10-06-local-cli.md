## 基线两条失败的真实原因（测试时序，非取消语义）

[npm 包分发](2026-10-06-npm-package-distribution.md) 把这两条记为"取消请求已发出但原生终态未到达时不得改写成 cancelled"的语义问题。本次逐步定位后，**该解读不成立**，产品代码的取消语义是对的，失败来自测试的等待预算小于本机的原生进程检查耗时。

用临时脚本（`.local/dbg-cancel.mjs`、`.local/dbg-spawn.mjs`、`.local/dbg-transport.mjs`、`.local/dbg-inspector.mjs`）按两条测试的条件复现，证据链：

1. 直接驱动传输层（`invokeCodexAppServerTurn` + fixture，`processEvidence: null`）完全正常：完整握手、`status: "succeeded"`、`native_status: "completed"`。
2. 经过 `CodexAdapter.dispatch`（带 `processEvidence`）时，fixture 子进程在收到 `turn/start` 之前就被 SIGTERM，**没有任何 stdout**；任务以 `cancelled / process_tree_unconfirmed / submission: not_sent` 结束，且 `adapter.cancel` 从未被调用。
3. 原因是 `createCodexAppServerProcessEvidence.inspect()` 在 `child.once('spawn')` 里 await 的 `inspector.inspectProcess()` 尚未返回，而 `execution.observation_timeout_ms` 已经到点。
4. 实测本机 Windows 进程检查耗时（`.local/dbg-inspector.mjs`，同一子进程重复 3 次）：`inspectProcess` 1516 / 1585 / 1561 ms，`inspectProcessTree` 1732 / 1846 / 1607 ms。
5. 两条测试用 `for (let i = 0; i < 100; i++)` + 10 ms 轮询等待 `dispatch.accepted`，预算只有 **1 s**；实测接受发生在 **~1.56–1.75 s**，因此轮询必然先超时，测试在**发送前**就发起取消。
6. 发送前取消被正确归为 `cancelled`（`worker.mjs` 中 `cancel_requested && submission === 'not_sent'`），与测试期望的"已接受后不确定"语义矛盾。测试 A 的 `observation_timeout_ms: 1_000` 本身也低于检查耗时，即使只放宽轮询也会先被自己的截止时间打断（复现为 `failed / process_tree_unconfirmed`）。
7. 把截止时间放宽到 10 s 并等待到 `dispatch.accepted` 后，两条场景都得到测试所断言的完整结果：`status = indeterminate`、`native.status = unknown`、错误码存在（`native_process_forced_stop` / `cancel_remote_state_unknown`）、`native_outcome = null`，事件序列为 `dispatch.accepted` → `control.cancel_requested` → `task.indeterminate`，**没有任何改写为 `cancelled`**。

结论：这是**测试等待预算不足**（固定 1 s 轮询与 1 s 截止时间小于本机约 1.5 s 的进程检查成本），不是产品缺陷，也不是本次未提交改动引入。修法是让等待上限由 `observation_timeout_ms` 推导（至少大于一次进程检查耗时），并在测试 A 中同步放宽 `observation_timeout_ms`。

复核进行中，工作树里这两条用例还被另一处改动显式跳过（`{ skip: 'pre-existing baseline red: racy cancel/observation outcome' }`）。[npm 包分发](2026-10-06-npm-package-distribution.md) 给出的理由是"观察结束"与"取消请求"之间的竞态，把断言对齐到任一侧都会不稳定。本次测量不支持这个理由：把等待上限放宽到覆盖一次进程检查耗时（10 s 截止时间 + 等待到 `dispatch.accepted`）后，两条场景各跑 3 次共 6 次，**全部**为 `indeterminate` + `native.status = unknown`，接受时间 1499–1818 ms，没有出现两侧的随机落点。因此这不是无法对齐的竞态，而是"固定 1 s 轮询短于约 1.5 s 检查耗时"的确定性错配；跳过会把可修复的覆盖缺口固定下来。本次未改动该测试文件（另一写者正在改）。

后续（同一工作树的另一轮）：那个“另一写者”就是本轮改动。它先按“注释掉失败测试”的要求把这两条改成 `{ skip: ... }`，在读到本记录后取消 skip，并按上述修法只改等待预算（`CANCELLATION_OBSERVATION_TIMEOUT_MS = 10_000`、轮询上限 100 → 1_000）而不改任何断言；同一文件中断言 `succeeded` 的其余用例改用 `FIXTURE_OBSERVATION_TIMEOUT_MS = 30_000`，用于消除同一类负载敏感（本轮用 14 个进程制造 CPU 饥荒复现了 `process_tree_unconfirmed`，证明该文件其他用例也处于同一风险下）。复验：该文件 37/37 通过、0 skip；完整 `npm test` 473/473、退出码 0。详见 [npm 包分发验证](2026-10-06-npm-package-distribution.md)。

## trae 构建修复（本次唯一代码改动）
